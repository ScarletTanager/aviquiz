# Shared photo review

Open `/review` on the quiz site. Only the owner can edit. Existing viewers can use approved tips but cannot read review drafts or write reviews. Sites supplies authenticated identity headers; the Worker checks the owner account ID or the configured owner's verified email on every operation (request IDs can be Site-scoped). `REVIEW_OWNER_EMAIL` is a server-side configuration value, never a browser field. The site's existing audience is unchanged.

The workspace shows coverage, a taxonomic breadth-first queue, site/family filters, and batches of 10, 20, or 50 species. Each queue entry proposes one candidate per species. The first global round prioritizes species without an approved image; round two begins once each species with remaining usable candidates has one. Existing extra pilot images are retained. Filters do not bypass the global round. Skipping every candidate flags the species as needing replacement rather than silently claiming coverage.

Select an existing species to revisit drafts or approved photos. Inspect the Macaulay photo and its eBird/Merlin source account. Enter paraphrased general tips, up to two short visible-feature callouts, and arrow positions by clicking the displayed photograph. The preview uses the original uncropped image with labels outside it. Source and photo checks are required for approval. No screen capture is needed. Metadata does not establish a feature’s visibility: inspect each actual image. Sex, age, and geographic caveats belong in general tips where relevant.

Draft saves are server-side and shared across devices. Approval publishes a snapshot, separate from the editable draft. Editing an approved entry leaves its last approved snapshot live until reapproval. Withdrawal removes that photo's published snapshot. A revision guard rejects stale edits instead of overwriting another tab's work. Refresh before resolving a conflict. Unsaved edits remain in the tab with a navigation warning. Export downloads a JSON backup of the currently loaded shared state; refresh first for the latest server state.

Quiz startup and each new quiz load approved snapshots from `/api/annotations` without caching. Approved photo callouts work across all families. Other photos of a covered species use general tips, with the latest approved species summary taking precedence. Drafts, notes, and checkboxes are not sent to quiz visitors. Opt-in and wrong/revealed-answer gating remain in effect. The original three species summaries remain a built-in fallback. If the shared endpoint fails, the quiz uses its last loaded tips or the original pilot; it explains this on the homepage. No code deployment is needed for review saves or approvals.

Attribution remains visible with the tips: eBird / Merlin, Cornell Lab of Ornithology, with a direct account link. Our paraphrases and placements are experimental adaptations, not Cornell-reviewed or endorsed annotations. Photograph credits and Macaulay record links are retained. These are pointers, not complete identification keys.

## Agent batches

`scripts/review-agent.mjs` reads a JSON instruction from stdin. It supports `seed` (idempotently imports the original six reviewed photos), `exportPath` (saves the current state), and `batchPath` (a JSON file containing `{action, document}` entries). Actions are `draft`, `approve`, `skip`, or `unpublish`. Approvals require the same checked source/image criteria as the UI and obey the breadth-first rule. The client reads current revisions, works sequentially, and stops on a failure. Already approved entries are skipped unless `skipApproved:false` is supplied. It never automatically approves uninspected photographs.

Each document contains `speciesId`, `photoId`, the exact `https://ebird.org/species/<speciesId>` source, `width`, `height`, general `tips`, up to two `features` (`title`, one or two short `lines`, normalized `[x,y]` `point`), `notes`, `photoChecked`, and `sourceChecked`. Validation rejects unknown photos, wrong source URLs, out-of-image coordinates, oversized labels, incomplete approvals, and stale revisions. Use the actual image dimensions. Download/inspect source photographs with image tools, render annotation proofs, check the placements, then approve. Work one photo per uncovered species before returning to an already covered species.

Batch access uses a separate server-side `REVIEW_AGENT_KEY`, configured as a Sites secret. Its matching local key is in `.review-agent.json` (mode 0600, ignored by Git); never put it in a batch, source, output, or browser code. The current workspace can therefore do future batches without requesting the owner's clicks. Retrieve the Site's supported service credential using `get_site` and supply it as `serviceToken` through stdin only; do not persist that platform token. No service credential is in the repository. If moving to another machine, securely provision the existing agent key or use the owner UI; do not casually rotate it. The server requires both the normal Sites access boundary and the review key for agent writes.

## Hosting and checks

The static quiz source remains in `dist/`. `scripts/build-worker.mjs` embeds those authored assets and the shared API into ignored `dist/server/index.js`. It follows the lightweight Worker ESM deployment layout and needs no dependencies. `.openai/hosting.json` retains the existing project identity and declares the `DB` D1 binding. Sites applies the schema-only migration under `drizzle/` before uploading the Worker. Do not edit an applied migration. Review content is data seeded/written through the API, not migration data or a deployment artifact. No photos are bundled.

Run `node test.mjs`, `node scripts/build-worker.mjs`, then `node test-review.mjs` with Node 24 or newer. Review tests use real SQLite via `node:sqlite` behind a D1-shaped adapter to exercise storage and routes, not only mocked SQL returns. Browser interaction QA has not been run for this workspace because screen capture is disabled. Keep the existing static-development option for quiz-only work; shared APIs require a Worker/D1 environment. Deploy with the Sites source helper, preserving the current audience, then use the batch client for content changes. Back up live reviews before bulk edits.

Audio quizzes are a separate future workstream. Keep their answer history, accuracy statistics, and mistake-review pools separate from visual practice; existing history is visual. This workspace does not change learning history or implement audio selection.
