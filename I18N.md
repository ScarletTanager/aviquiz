# Internationalization

AviQuiz uses pinned **i18next 27.2.9** for application messages in the browser,
Worker, and standalone Node server. English is the default; Colombian Spanish (`es-CO`) is available through the
header selector. The site remembers an explicit choice in a functional preference
cookie. There is no browser-language detection or remote translation service.

## Source ownership

| Location | Purpose |
| --- | --- |
| `locales/en/*.json` | Canonical English source messages, grouped by page or module; `common.json` provides shared messages and plurals. |
| `locales/<language>/families.json` | Localized family display names, keyed by stable scientific family identifiers. |
| `pages/*.html` | Canonical page templates. Edit structure here, rather than generated HTML. |
| `dist/i18n.mjs` | Shared `t`, `messageError`, and `locale` interface. Initializes i18next synchronously from bundled resources. |
| `scripts/build-i18n.mjs` | Generates English and Spanish HTML, resources, pinned vendor runtime/license, and domain-data modules. |
| `dist/messages-*.mjs`, `dist/i18next.mjs`, `dist/*.html` | Committed generated assets, checked for deterministic regeneration. |
| `data/*.json` | Supplemental species/photo records and locality matching aliases, separate from translatable UI messages. |

The bundles include navigation, regular and experimental quiz text, configuration
labels, help, dialogs, statistics, consent, backup/import, invitations, review
workspace, accessibility labels, built-in identification tips, and application
validation/API errors. Provider-library diagnostics and operational CLI/log
messages are not an end-user translation surface.

Species names, scientific names, place names, contributor credits, dates, and
user-authored trip names or review documents are domain content. They remain in
catalogs, external data files, or database records and are interpolated into
messages. This refactor does not translate that content or change name matching.
A future species-name localization project must preserve scientific identity,
accepted-name aliases, and attribution. Existing geography metadata also retains
its provider-supplied place names.

## Editing text

1. Edit the appropriate `locales/en` JSON file. Values must be strings.
2. Retain a message's existing key when revising wording. Initial migrated keys
   have a readable slug and hash for uniqueness; the hash is not regenerated on
   wording changes. New keys should use descriptive stable names.
3. Use a complete sentence/message where possible, with named interpolation
   parameters for new messages. Do not assemble grammatical endings in code.
   Migrated positional `v0`, `v1`, etc. parameters are explicitly checked and can
   be renamed in a coordinated source/bundle edit.
4. Build and test:

   ```sh
   npm ci --ignore-scripts
   npm run build:i18n
   npm run test:i18n
   node scripts/build-worker.mjs
   ```

`build-worker.mjs` also runs the message build automatically. Commit both source
bundles/templates and generated assets. CI rejects stale generated output, missing
references, mismatched interpolation parameters, hardcoded page text, direct
literal DOM display assignments, and incomplete English plural pairs.

### JavaScript

```js
import {t, locale, messageError} from './i18n.mjs';
label.textContent = t('common:locationCount', {count: locations.length});
const date = new Intl.DateTimeFormat(locale).format(value);
throw messageError('geography-core:choose_a_valid_year_and_month_9dbc8897');
```

Use an existing key from the relevant bundle.
Unknown keys throw rather than appearing in the UI. `messageError` retains
`messageKey` for stable classification: never compare rendered English to decide
an HTTP status, permission, storage key, or application branch.

Plural forms use i18next's `_one` / `_other` convention and numeric `count`:

```json
{
  "locationCount_one": "{{count}} location",
  "locationCount_other": "{{count}} locations"
}
```

Call `t('common:locationCount', {count: n})`, without the suffix. Other languages
may need additional plural categories. Keep IDs, enums, URLs, SQL, CSS classes,
HTTP headers, OAuth scopes, file names, and matching aliases out of translations.
Never translate `Bearer`, for example.

### HTML templates

A text/rich-content marker is `<!--msg page-index:existing_key-->`. An attribute
marker is `@@msg:page-index:existing_key@@`. The build resolves these for each supported language;
attribute values are HTML-escaped. Keep control structure and IDs in templates.
Static pages remain readable without JavaScript and do not flash message keys.

Some migrated messages retain existing inline HTML or complete legacy rendering
fragments so their visible text can be translated together. Preserve their
structural attributes, links, element IDs, and interpolation slots when editing.
Do not introduce scripts, event handlers, or executable URLs into messages.

### Escaping and external content

`t` returns **plain text** and deliberately does not HTML-escape interpolation:
`textContent`, form values, and JSON must receive literal text, not entities.
i18next does not re-evaluate interpolation supplied by a user as another message.

For legacy `innerHTML`/SVG renderers, continue escaping every external string at
its insertion point using that renderer's existing escape helper. Only reviewed,
application-owned markup may be passed as a rich fragment. Translating a message
does not make a user-provided string safe HTML. The existing annotation escaping
regressions and `test-i18n.mjs` exercise these boundaries.

## Packaging and verification

The Worker build embeds the generated pages and browser resources and bundles
the shared message runtime into server code. The DigitalOcean packager also
copies `dist/i18n.mjs`, both `dist/messages-*.mjs` files,
`dist/locale-preference.mjs`, `dist/i18next.mjs`, and its license,
because standalone server adapters import that runtime directly. No npm/network
translation loader runs at request time.

Run `npm run test:i18n` and the application regressions listed in
[DEPLOYMENT.md](DEPLOYMENT.md) before packaging. No AWS account action is needed
to build or test messages locally.

## Adding a language later

For a language without existing draft bundles, add them under
`locales/<language>/`. Validate key and parameter
parity, extend the build to emit that language's page/resources, and explicitly
choose how a user preference reaches both browser and server. The current build
targets English and Colombian Spanish. Extend the existing preference handling,
fallback and plural tests, language/formatting tests, translated rich-content
review, and layout/accessibility checks. Server and browser must use the same
selected locale. Taxonomic names and user content require a separate policy;
copying application bundles alone does not translate them.

## Colombian Spanish draft bundles

`locales/es-CO/` contains a complete first translation pass corresponding to all
English bundles. The locale is deliberately specific to Colombia. Its register
is clear, educated Bogotá Spanish, using **usted**, restrained phrasing, and
Colombian/Latin American vocabulary rather than peninsular Spanish. It avoids
voseo, informal regional slang, and Spain-specific forms such as *vosotros*,
*ordenador*, and *fichero*.

Preferred terminology:

| English | Spanish convention |
| --- | --- |
| Quiz | Cuestionario |
| Sign in / sign out | Iniciar sesión / cerrar sesión |
| Checklist | Lista de aves |
| Trip / stop | Viaje / parada |
| Photo / recording | Foto / grabación |
| Mistake review | Repaso de errores |
| Photo review / approval | Revisión de fotos / aprobación |
| Correct ID rate | Porcentaje de aciertos |
| Lifer | Especie nueva para su lista de vida (mundial o de Colombia) |
| Hotspot | Sitio de interés de eBird |
| File / browser tab | Archivo / pestaña |

Family labels are translated descriptive group names; stable scientific family
keys are unchanged. Species names from the catalogs, user-authored content,
source attributions, and URLs remain unchanged. References to named species in
built-in identification tips retain the catalog's English name to avoid
introducing a second species-name convention before species localization exists.

These bundles are available through the header selector. Native speakers should
review layout, long labels, legacy sentence fragments, and birding terminology
in staging before production promotion. In particular, literal fragments inherited from English may need
whole-sentence call-site refactoring to support Spanish gender and word order.

`npm run check:i18n` validates every locale directory against English: namespace
and key parity, interpolation occurrence parity, nonempty values, safe markup,
and preserved HTML/SVG structure and attributes (including links and control
identifiers). `npm run test:i18n` also creates an isolated Spanish i18next
instance, exercises every message, verifies plurals and named values, and
confirms English remains the default. These tests do not require a live service.

## Header selection and request isolation

Every page has an accessible Language / Idioma select with English and
Español (Colombia). English is used when there is no valid preference, regardless
of the browser's language. An explicit choice sets `aviquiz-language` for one
year, host-only, Path=/, SameSite=Lax, and Secure on HTTPS. This functional cookie
is independent of optional statistics consent and contains only `en` or `es-CO`.
It is not an account setting and does not clear, export, or migrate statistics.
Staging and production retain independent preferences.

Changing the language reloads the current URL, preserving its path, query, and
fragment. An unfinished quiz or user-edited fields trigger confirmation before
reload; canceling preserves the current page and choice. Unsaved in-memory work
is not migrated between languages. Sign-in return URLs remain unchanged; the
preference cookie survives the round trip. Provider-managed sign-in pages are
outside this application selector and have not been reconfigured.

The build emits default `index.html` etc. and `index.es-CO.html` etc. The Worker
chooses an allowlisted HTML variant using the request cookie and returns
Content-Language and Vary: Cookie with no-cache. The browser initializes i18next
from the rendered document's language before quiz modules initialize, so static
text, dynamic labels, family names, month names, and number formatting agree.
Both language resources are bundled locally; no language fetch race is needed.

Server modules continue emitting the existing English API message contract.
`worker/localized-response.mjs` is a request-specific presentation adapter: it
recognizes application-owned messages from the bundles (including named slots)
and translates only top-level error/notice/message strings. Status codes, data,
IDs, nested user documents, and audit events are unchanged. Unknown diagnostics
pass through unchanged. Matching is for presentation only, never authorization
or error classification. No request changes a shared translator's language, so
simultaneous English and Spanish requests are isolated. New APIs should prefer
explicit message keys and parameters to extend this legacy contract.

Run `npm run test:language` to build and exercise both languages on all page
routes, concurrent responses, API notices/errors, HEAD/cache behavior, selectors,
cancellation, and actual Spanish family/date initialization.
