# Internationalization

AviQuiz uses pinned **i18next 27.2.9** for application messages in the browser,
Worker, and standalone Node server. English is currently the only enabled
language. There is no language selector, browser-language detection, translation
service, language cookie, or additional remote request. This refactor prepares
message ownership and rendering; it does not add another language.

## Source ownership

| Location | Purpose |
| --- | --- |
| `locales/en/*.json` | Canonical English application messages, grouped by page or module; `common.json` provides shared messages and plurals. |
| `locales/en/families.json` | English family display names, keyed by stable scientific family identifiers. |
| `pages/*.html` | Canonical page templates. Edit structure here, rather than generated HTML. |
| `dist/i18n.mjs` | Shared `t`, `messageError`, and `locale` interface. Initializes i18next synchronously from bundled resources. |
| `scripts/build-i18n.mjs` | Generates English HTML, resources, pinned vendor runtime/license, and domain-data modules. |
| `dist/messages-en.mjs`, `dist/i18next.mjs`, `dist/*.html` | Committed generated assets, checked for deterministic regeneration. |
| `data/*.json` | Supplemental species/photo records and locality matching aliases, separate from translatable UI messages. |

The bundles include navigation, regular and experimental quiz text, configuration
labels, help, dialogs, statistics, consent, backup/import, invitations, review
workspace, accessibility labels, built-in identification tips, and application
validation/API errors. Provider-library diagnostics and operational CLI/log
messages are not an end-user translation surface.

Species names, scientific names, place names, contributor credits, dates, and
user-authored trip names or review documents are domain content. They remain in
catalogs, external data files, or database records and are interpolated into
messages. This refactor does not translate that content or change name matching.
A future species-name localization project must preserve scientific identity,
accepted-name aliases, and attribution. Existing geography metadata also retains
its provider-supplied place names.

## Editing text

1. Edit the appropriate `locales/en` JSON file. Values must be strings.
2. Retain a message's existing key when revising wording. Initial migrated keys
   have a readable slug and hash for uniqueness; the hash is not regenerated on
   wording changes. New keys should use descriptive stable names.
3. Use a complete sentence/message where possible, with named interpolation
   parameters for new messages. Do not assemble grammatical endings in code.
   Migrated positional `v0`, `v1`, etc. parameters are explicitly checked and can
   be renamed in a coordinated source/bundle edit.
4. Build and test:

   ```sh
   npm ci --ignore-scripts
   npm run build:i18n
   npm run test:i18n
   node scripts/build-worker.mjs
   ```

`build-worker.mjs` also runs the message build automatically. Commit both source
bundles/templates and generated assets. CI rejects stale generated output, missing
references, mismatched interpolation parameters, hardcoded page text, direct
literal DOM display assignments, and incomplete English plural pairs.

### JavaScript

```js
import {t, locale, messageError} from './i18n.mjs';
label.textContent = t('common:locationCount', {count: locations.length});
const date = new Intl.DateTimeFormat(locale).format(value);
throw messageError('geography-core:choose_a_valid_year_and_month_9dbc8897');
```

Use an existing key from the relevant bundle.
Unknown keys throw rather than appearing in the UI. `messageError` retains
`messageKey` for stable classification: never compare rendered English to decide
an HTTP status, permission, storage key, or application branch.

Plural forms use i18next's `_one` / `_other` convention and numeric `count`:

```json
{
  "locationCount_one": "{{count}} location",
  "locationCount_other": "{{count}} locations"
}
```

Call `t('common:locationCount', {count: n})`, without the suffix. Other languages
may need additional plural categories. Keep IDs, enums, URLs, SQL, CSS classes,
HTTP headers, OAuth scopes, file names, and matching aliases out of translations.
Never translate `Bearer`, for example.

### HTML templates

A text/rich-content marker is `<!--msg page-index:existing_key-->`. An attribute
marker is `@@msg:page-index:existing_key@@`. The build resolves these to English;
attribute values are HTML-escaped. Keep control structure and IDs in templates.
Static pages remain readable without JavaScript and do not flash message keys.

Some migrated messages retain existing inline HTML or complete legacy rendering
fragments so their visible text can be translated together. Preserve their
structural attributes, links, element IDs, and interpolation slots when editing.
Do not introduce scripts, event handlers, or executable URLs into messages.

### Escaping and external content

`t` returns **plain text** and deliberately does not HTML-escape interpolation:
`textContent`, form values, and JSON must receive literal text, not entities.
i18next does not re-evaluate interpolation supplied by a user as another message.

For legacy `innerHTML`/SVG renderers, continue escaping every external string at
its insertion point using that renderer's existing escape helper. Only reviewed,
application-owned markup may be passed as a rich fragment. Translating a message
does not make a user-provided string safe HTML. The existing annotation escaping
regressions and `test-i18n.mjs` exercise these boundaries.

## Packaging and verification

The Worker build embeds the generated pages and browser resources and bundles
the shared message runtime into server code. The DigitalOcean packager also
copies `dist/i18n.mjs`, `dist/messages-en.mjs`, `dist/i18next.mjs`, and its license,
because standalone server adapters import that runtime directly. No npm/network
translation loader runs at request time.

Run `npm run test:i18n` and the application regressions listed in
[DEPLOYMENT.md](DEPLOYMENT.md) before packaging. No AWS account action is needed
to build or test messages locally.

## Adding a language later

Add corresponding bundles under `locales/<language>/`, validate key and parameter
parity, extend the build to emit that language's page/resources, and explicitly
choose how a user preference reaches both browser and server. The current build
intentionally targets English only. Then add locale-aware routing/selection,
fallback and plural tests, language/formatting tests, translated rich-content
review, and layout/accessibility checks. Server and browser must use the same
selected locale. Taxonomic names and user content require a separate policy;
copying application bundles alone does not translate them.
